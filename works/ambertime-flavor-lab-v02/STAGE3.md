# 第3段階：瓶詰めから街へ

基準はPR #589後のmain `5ee378230025b70c27567b3b395df61f83516039`。PR #588の名前の成長、#589の伝播規則は再設計しない。変更は瓶詰めの一方向の受け渡し、既存商品入力への変換、最小表示と検証に限定した。Production・AmberTime本編は対象外。

## 個性の変換

名前の文字列ではなく、保存済みの瓶のspirit・months・choiceから既存のprofileForで得る瓶詰め時点の8特徴を正本とする。

| 街の既存軸 | 変換 |
| --- | --- |
| roughness（刺激） | roughをそのまま |
| character（原酒香） | fruit・grain・smoke・bodyの最大値 |
| wood（樽香） | wood・vanillaの最大値 |

果実・穀物・煙・厚みは、それぞれ目立つときに原酒香の強さへ反映される。煙を刺激へ置き換えない。spiceは3軸へ使用せず、全8特徴を記録に残す。最大値を取るため、異なる香りでも同じ3軸になる場合がある。街に果実好き・煙好きの専用の好みはなく、相性は香りの種類そのものを区別できない。これは既存3軸の限界であり、今回新軸を追加しない。

## 操作と固定情報

名前Labで瓶詰め後、瓶の「街へ送り出す」を押す。固定ID・表示名・8特徴・主な個性・熟成月数・原料/発酵/蒸留範囲/樽・元の瓶ID/瓶詰め月・数量24・発売月0を検証済みURLフラグメントに収め、街へ移動する。街の通常表示は名前、主な個性、熟成年数と供給の仮定だけを示す。詳細には発売回と元の固定IDを残す。無効な受信データは理由を表示して受理しない。

IDは元の瓶と内容から計算する同一レコード用の安定IDで、世界全体での物理ボトルの識別や改ざん防止署名ではない。表示名はIDと相性計算に使わない。受信データはコピーして深く固定し、元の樽の熟成や次の仕込みに追従しない。双方向同期や新しい保存キーはない。

街では既存の継続供給を使い、受け取った風味を18か月ごとに24本ずつ仕込む仮定を明記する。準備期間24か月・価格30は比較全件で固定。実際の瓶の熟成年数は出自として保持し、生産待ち時間へ流用しない。輸入した風味には既存のランダム揺れや再熟成を加えない。これは一本分24本だけで終了する販売システムではない。既存の供給・在庫・納品・定着をそのまま観察する接続である。

## 小規模比較

シード20261021、同じ街・初期条件、数量24・発売月0、30年。果実・厚み・煙の3本に、同じ果実原酒の樽違いと熟成期間違いを加えた計5本を用いる。樽差と年数差を混ぜずに比較する。追加シード探索はしていない。穀物の対応は単体テストのみ。

| 瓶 | 表示名 | 相性が最も高い相手 | 関心 / 問い合わせ / 共有 / 来訪 |
| --- | --- | --- | --- |
| 果実・3年リフィル | 果実香が強い | 全国の飲食のつながり | 86 / 42 / 17 / 10 |
| 厚み・3年リフィル | まろやかで厚みのある味 | 専門酒店 | 72 / 33 / 16 / 8 |
| 煙・3年リフィル | 煙の香りが豊か | 町の酒店 | 80 / 36 / 19 / 10 |
| 同じ果実・3年1stフィル | 果実香が強い | 全国の飲食のつながり | 95 / 44 / 18 / 14 |
| 同じ果実・8年リフィル | 穏やかな果実香 | 全国の飲食のつながり | 83 / 39 / 17 / 10 |

相性の順位は実際の取扱い獲得を保証しない。全件で生産480・納品360・在庫120。30年後に好まれ、取扱いがある先は同じ5地点（町の酒店・食堂・周辺の食文化圏・全国の飲食のつながり・海外の飲食文化圏）だった。今回の範囲で「最終的な取扱地域が分かれた」とは言えない。相性、反応件数、時期には差があり、同じ名前の樽違いでも結果が変わった。長く熟成したものが一律に優位にはならない。詳細な入力・3軸・相性・集計・出来事は[stage3-results.json](stage3-results.json)。

例：果実3年では1年10か月に「食堂で『果実香が強い』が好みに合い、関心を持たれました」。全件4年6か月に町の酒店の発信者を通じて海外の熟成酒文化圏への紹介が生まれる。紹介の理由と、その後の好みに合う/合わない反応は既存規則のまま別に残る。到着数は1137〜1153だが、それがそのまま人気や定着を意味しない。

## 保存・再現と検証

名前Labのversion2保存キー・構造は変更しない。既存瓶も送信時にスナップショット化できる。街は元々自動保存を持たず、再読み込みではURL内の商品を保持して0か月から始める。経過と途中設定の保存は既存JSON出力を使う。

街の`ambertime-town-log/1`に、任意の`initialConditions.productSnapshot`だけを追加する。自由な瓶の再現にはこの入力が不可欠。各発売回の汎用product記録には元のspecimenId・label・primaryLabelを加える。通常の比較商品は従来の出力構造と結果を維持する。旧ログは引き続き再現できるが、新しい任意入力を含むログの再現には第3段階のコードが必要。モデルの相性・伝播規則は変更せずmodelVersionは0.1.1のまま。

検証コマンド：

```sh
node works/ambertime-flavor-lab-v02/test.mjs
node works/ambertime-flavor-lab-v02/browser-test.mjs
node works/ambertime-flavor-lab-v02/bridge.test.mjs
node --test works/ambertime/experiments/town-simulation/v01/model.test.mjs
```

受信検証、旧保存の非破壊、深い固定、名前だけ変えても同じ結果、同名で異なる個性、樽差・年数差、供給の固定、途中商品切替とJSON完全再現を確認する。既存街8テストと従来比較結果を維持。公開配信・実操作・CIの証拠は作業PRへ記録する。異なるJavaScript実装間の浮動小数点末尾差は許容し、出来事・因果・数量の一致を確認する。

## 終了と第4段階への引き継ぎ

第4段階へは、この固定スナップショット、3軸変換、商品と発売回の識別、供給の仮定を渡す。本編の数量・発売月・供給の扱いは本編接続時に決める。今回のURL接続を本編の永続保存や販売仕様とみなさない。8特徴を3軸へ縮める限界と、今回同じ取扱地域へ至った結果を判断材料にする。大規模なモデル調整は行わない。

作者による数本の仕込み・送信・街の観察、面白さと採用の判断は未確認。自動テスト成功だけで面白さを確認済みとはしない。物理iPhone/Safariでの操作も未確認。実装と公開操作の確認後、作者がこの流れを評価できる状態で第3段階を区切る。
