# 正式保存の可逆表現・容量候補

基点 main 0778bcf4555737ec45947a80aca8f761f39fa429。r0 を実装より先に固定。Stage4 #927 の経済変更とは分離した前提変更であり、現時点では本編の保存形式を自動変更しない。

## 変更

旧 native JSON と正式v8の容量・形式・検査経路は維持。新しい `ambertime-exact-json/1` は同じオブジェクトキー配置と、反復する長い文字列を辞書参照で表す。元のすべての配列・値・キー順序を残す。操作、町の出来事、回想、世代、帳面を削除しない。展開文字列は元のcanonical JSONと完全一致する。

native restoreは明示された新envelopeだけを有限予算で展開した後、従来の完全なvalidate/replayを実行する。正式v9はlogical v8全体（sidecar含む）を包む。正式readerはv8/v9を区別し、どちらもmode・elapsed・native再生・全sidecar検査を行う。serializerの既定はv8のまま。`encoding:'lossless-v1'` を指定した場合だけv9を出力する。isCurrentSessionは対応版8/9の判定であり、記録内容の妥当性は正式readerで検証する。

## 固定した資源境界

native/codec入力は従来と同じ6,016,384 code units未満。正式sessionは6,017,408未満。新表現の展開後は16,777,216 UTF16 units以下、展開ノード1,000,000以下、深さ32以下、shape4096以下、値文字列65,536以下、object幅16,384以下、array長131,072以下、quoted key/value長65,536以下。文字列参照の繰返しも毎回出力長へ加算し、書出し前に停止する。object参照や循環参照は表現できない。旧v8の上限は変えない。

canonicalな再エンコードとの一致で余分な辞書・順序差・別名表現を拒否する。JSON textとして安全に復元するので `__proto__` 等のキーを勝手に落とさない。

## 実測と限界

#927の実ゲーム1200か月原本から独立して測定した地域経路nativeは5,792,137 units、local経路は11,294,059 units（653,805 nodes、深さ9、最大object幅8992）。実装codecはそれぞれ2,824,372 unitsと5,613,807 unitsに可逆変換し、SHA256と全文比較が一致。旧codec上限を単純に増やしたのではなく、同じwire上限内に収めている。

これだけで正式100年保存を合格とはしない。#927との統合後、5戦略の全sidecar、別プロセス、翌月、初回再保存、再度の別プロセス、独立した元状態比較が必要。旧「分散」は1窓口だったので真の分散検証の代用にしない。実際の2窓口の契約と実売を使った別の経営基点を準備する。

新形式は本編IDB接続・世代保護・title/import/export・cache closureを別の統合段階で確認するまで有効化しない。元記録や旧世代は変更しない。iPhoneの容量・メモリ・応答速度は未確認。この資源上限は形式の有限性を守るもので、実機で快適という保証ではない。

## 戻し方

v9を書き始める前はこの前提変更を戻せる。v9が存在した後はreaderと書出し機能を保持し、旧v8へ無理に読み替えない。読めない記録を消したり、正常世代の検証を省いたりしない。

## 初期回帰結果

新codec・正式保存と既存保存回帰を合わせ56/56成功。追加のv9別プロセス試験を含む正式v9試験4/4成功（前記との重複あり、合計60件とは数えない）。資源境界はcap−1/cap/cap+1、canonicalなwire境界、shape・文字列辞書・深さ・幅・array・展開ノードで確認。250生成ケース、Unicode／孤立surrogate、キー順序、prototype風キー、参照改ざん、未使用辞書を検査。

保存メニューの既存2試験は `debugSkipJob is not defined` で失敗し、正確な基点0778bcfの未変更app/index/testから同じ失敗を再現した。失敗を無効化せず、今回の修正で治ったとは扱わない。旧形式を単にversion9へ書換えた記録は従来通りunsupportedとし、実際の新envelopeだけをv9として認識する。
