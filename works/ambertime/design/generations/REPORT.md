# AmberTime 0.17 — 世代交代と最後の仕込み

世代番号と、先代の最後の一樽の来歴を追加した。資金・設備・原酒・商品・銘柄・取扱店・契約をリセットせず、同じ蒸留所を続ける。蒸留・熟成・需要・価格・評判・最大4樽の計算は変更しない。Productionは対象外。

## 発生条件と期間の比較

| 状態 | 条件・処理 |
| --- | --- |
| 通常期 | 各代の就任から300か月未満。引退通知・任意の引退ボタンなし |
| 晩年期 | 300か月（25年）以降。実際の出来事があれば最後の仕込みへ進む |
| 実際の節目 | 作成から120か月以上の銘柄の再発売、36か月以上の原酒の瓶詰め、銘柄×店舗の関係成立から120か月以上経った納品 |
| 最終期限 | 就任から360か月（30年）。節目がなくても最後の仕込みへ進む |
| 樽詰めの猶予 | 確定から12実経過月。未完了なら今ある原酒・樽を引き継ぐ |

先に旧版40年の実操作履歴から25/30年、25/35年、30/35年を比較し、25/30年を採用した。25年目の再発売は熟成12か月の銘柄であり、長期熟成だけを評価しない。25/35年は同じ最初の機会を拾い、出来事のない場合の待ちだけ延びる。30/35年は最初の機会が約5年遅れる。

現行時計は1か月6秒。25・30・35年は時計だけなら30・36・42分、猶予12か月は72秒。モーダル・手動停止・操作・読む時間は含まない。年数や最後の操作への愛着が適切かは人間の試遊で確かめる。詳細と元保存のハッシュは `comparison-notes.md`、`comparison-results.json`、比較CSVを参照。

資金保護で月次そのものを進められない例外も扱う。25年以降の実際の月次試行で資金停止が再現される場合は、その月の「資金の状況」を記録して引継ぎレビューへ進む。最後の仕込み期間中も同様。架空の月を足さず、既存の資金保護や費用を変更しない。資金のある通常期は、樽や販売中商品がなくても時間を進められる。初期資金だけで運営をしない検査では302か月でこの例外に至った。25年未満の既存の資金停止は維持する。

## 最後の仕込みと引継ぎ

節目の出来事と年月を一度だけ通知する。今ある瓶詰め直後の詳細・樽判断・取引の申し出を先に扱い、進行中の蒸留に割り込まない。

通知後は普段と同じ開始、変化の観察、抽出停止、樽選択、樽詰めを手動で行う。新しく開始した一仕込みだけを最後の仕込みと識別する。費用・容量・風味は通常と同じ。以前から進んでいた蒸留や「いつもの仕込み」を最後の一樽として付け替えない。

4樽や商品枠が埋まっている場合は、通常の熟成・瓶詰め・販売・納品を続けて空きを待てる。12か月たっても作れなければ「仕込まず」、抽出中なら「樽詰め前」と記録する。強制瓶詰め・廃棄・追加の樽はない。進行中の蒸留や原酒もそのまま次代へ引き継ぐ。

予約中の「いつもの仕込み」は予約を保持して自動開始を待つ。先に開始済みなら元のレシピで通常通り完了し、その後に最後の手動仕込みを行う。引継ぎ後は予約が再び通常条件で開始可能になる。

最後の樽詰め、猶予終了、資金停止のいずれかで短いレビューを開く。在任年月・実際の契機・最後の樽または未実行の事実だけを表示する。「蒸留所の歩み」は任意で開け、閉じるとレビューへ戻る。重い年表の集計を待たずに引き継げる。

次代への引継ぎは世代IDを検査し、完了済みIDの再実行では何も変更しない。資金・設備・樽・蒸留中状態・保管／販売中商品・銘柄と製法・関係・通常卸売・特別注文・納品／採用履歴は直前と同一。月を戻したり追加したりしない。現行モデルは月単位なので、引継ぎ年月と次代の就任年月は同じ実月となる。手動停止していた場合はその状態を維持する。

## 来歴・年表・最小保存

`generations` に現在代と完了した各代の事実を保持する。番号、就任月、確定月と契機、最後の仕込みのbatch／cask ID、完了状態、引継月が正本。別の世代イベント台帳や商品ごとの重複した来歴タグは保存しない。

最後の樽のIDを、この正本から参照する。次代の貯蔵庫、ボトル詳細、銘柄の発売記録、完売後の記録にも「初代の最後の仕込み」等を表示する。次代が瓶詰め・発売時期や銘柄を決める。特別な品質・需要・評判補正なし。

既存の歩みの再生処理に世代の区切りを加える。実際の再発売や納品が契機なら元の出来事に付記し、別の重複イベントにしない。期限や資金停止は実月の事実を一件表示する。引継ぎは次代の就任も兼ね、一つの出来事にする。同月でも操作順から担当世代を得るので、先代の樽詰め→引継ぎ→次代の瓶詰めを取り違えない。原酒を仕込んだ代と瓶詰めした代は区別する。

## 保存互換性

実行契約をv16 `distillery-generations`、UI保存キーを `sukimastock.ambertime.wholesale.v16` に分離した。v15以下は従来規則で厳密復元してから、記録された `enable-generations` 境界で拡張する。旧操作を新規則で再解釈せず、既存の数値・契約・IDを変えない。

旧保存原文は旧キーに残す。`v0164.html` と既存アプリ／CSSの固定コピーから0.16.4を開ける。v16を旧版へ逆変換しない。旧版の販売中／保管中、価格、デパート限定取扱いと採用履歴も維持する。

初代は創業月0から数える。30年以上の旧保存を開いた場合は、移行した現在月で在任期限を記録する。過去の世代や、実行していない最後の仕込みは捏造しない。二代以降は実際の就任月から数える。

`generation-notice`、`generation-handover`、資金停止の操作は既存の帳面に記録する。蒸留途中の進行位置も従来の方法で復元する。保存・再読込で二重の最後の仕込みや二重の世代進行を起こさず、ID・就任月・引継月・樽ID・操作の改変は厳密検証で拒否する。

## 検証

Node全503テスト成功、失敗0。既存484件に世代モデル17件・世代来歴2件を追加した。独立レビューでも阻害事項なし。同月の樽詰め→引継ぎ→次代の瓶詰めの順序と、原酒の担当世代が保存後も一致することを別途検査した。

追加テストは実際の公開操作から、25年未満・実際の再発売／納品・30年期限・旧保存の40年超移行・最後の手動一回・満樽12か月・抽出途中の持越し・予約中／進行中のいつもの仕込み・資金停止・卸売契約・次代の在任期間・二重ID／改変拒否・完売と再発売後の来歴を確認した。最後の仕込みと従来版の同じ通常操作を並べ、費用と原酒が一致することも確認した。

実Chromium153でPC1280×900、iPhoneサイズ390×844の18シナリオ群が成功。実際の通知理由・発売回・期限、抽出位置40／65、瓶詰め直後の詳細優先、樽判断・店舗申し出優先、申し出列の維持、任意の歩みから必須レビューへ戻る操作、保存再読込・古い引継ぎボタン・自動／手動停止、満樽救済、次代の来歴、v15原文と旧版入口を検査した。横溢れ・pageerrorなし。6枚のスクリーンショットを目視確認。結果のソースハッシュは検証対象と一致する。実機Safariの結果ではない。

公開操作だけの2シード×1440か月（120年）が完了。各4回の引継ぎを経て五代目の通常運営へ進んだ。計8回の最後の仕込みはすべて通常の手動樽詰めで、自然な空きを最大7か月待った例もあった。各回の引継ぎ前後で資産・在庫・関係・契約等のJSON完全一致、樽数4以下、現金／在庫式、別プロセスの保存完全再現を確認した。

長期の初回処理は軽くない。シード1の年表1,390件の初回再構成は90.17秒だった。シード2の年表再構成は実行せず、保存の厳密復元まで確認した。既存の全操作再生と長期の帳面を用いるためで、最後の仕込み後の短いレビューはこの集計に依存しない。年表は既存Worker・キャッシュ・年選択・50件ページングを維持する。初回再読込／初回年表の待ち時間は今後の課題であり、瞬時に開けるとは扱わない。時間は共有検証環境の単発値。

復元長の上限は6,016,384コード単位未満で、ブラウザ容量とは別。発売512回・納品2,048件等の既存上限は維持し、古い出来事を削除していない。この方針で120年を確認した結果であり、無制限の継続保証ではない。将来の長期対策は厳密な来歴を保つチェックポイントの別設計が必要。

詳細は `long-results.json`、`long-runs.csv`、`long-transitions.csv`、`long-checkpoints.csv`、`long-notes.md`。蒸留・熟成・価格・需要・評判の保護対象7ソースと旧版アプリ／CSSのコピーは基準版のバイトと一致する。

## 再実行

```sh
cd works/ambertime
npm test
cd ../..
AMBER_COMPARE_ONLY=1 node works/ambertime/tests/generation-simulate.mjs
AMBER_SKIP_COMPARISON=1 node works/ambertime/tests/generation-simulate.mjs
node works/ambertime/tests/generation-browser.mjs
```

PlaywrightとChromiumが必要。ブラウザの実行ファイルは `AMBERTIME_CHROME`、シード・月数・出力先は `long-notes.md` を参照。ブラウザ用保存はChromium内の公開操作で作り、厳密再現を通す。Node生成の長期保存を異なる実行環境へ移す際の既存の浮動小数点差は今回修正しない。検証や数値の許容幅を緩めない。
