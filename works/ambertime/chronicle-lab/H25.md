## 実装と範囲

`recall-boundary.mjs` は候補を事前生成するAPI。

- `resolveRecallBoundary` が交代イベントIDと境界とシード用世代を返す。旧 `targetGeneration` は引き継ぎ元の指定として受け、シードは常に引き継ぎ先から決める。同じ交代は既定・ID・旧引数で同一結果になる。無効な明示指定はエラー。
- `prepareHistoricalCandidates` は `factStage='uncompressed'` の資料だけを受ける。月・操作番号・圧縮前位置で切ってから、現行の基準保持と世代別初回・記録された参照元というC-3条件を適用する。出力は `factStage='candidates'`。
- `buildHistoricalChronicle` は確定した候補と境界を既存D1.1へ渡す。評価、抽選、版は既存モジュールのまま。元の根拠・参照チェーンとイベントIDを保持する。
- 重複する同一事実は監査し、競合するIDは拒否する。欠損・未来・別発売の参照から到達を追加保持しない。内部伝播や直接到達は既存の抽出段階で表示候補から除外する。

C-3の条件を独立APIで表した部分は、H23Bの関数を直接呼んだ結果と実データで照合した。`editor.mjs` は事前候補のあるD交代回想を新経路へ渡す。従来資料から呼ぶH24研究とA/B/Cは従来経路を維持する。新APIでは第2・第3回のシードを引き継ぎ先3・4に統一するため、従来研究の明示指定2・3との結果差は候補修正と別に記録した。

## 閲覧用資料

`research-h25.mjs --archive` は事実の共有配列と、周年・各交代の候補ID・境界・シード世代・必要なordinal差分を生成する。各交代の履歴を丸ごと複製しない。Nodeの検証用コンシューマー `readRecallArchive` は資料から候補を復元し、ゲームを再生せず既存D1.1を呼ぶ。直接rawから生成した場面・監査情報と一致する。

公開ブラウザでは `recall-snapshots.mjs` が同じ候補を復元する。通常の30年資料には `facts-recalls.json`（14,811バイト）を追加し、既存の事実本文を共有する。交代ごとの候補IDとordinal差分を保持し、元保存のSHAと境界を検査する。周年は従来のC-3資料を使用する。

長期検証は同じLabの `?long=1` で開く。`facts-recalls-long.json` は3つの100年候補資料と各3交代の候補IDを含む1,167,033バイト。検証URLでだけ読み込む。回想時点が交代の場合だけ「引き継ぎ」を選択でき、1交代しかない通常資料では選択欄を隠す。検証メニューを小画面に収める調整に限定し、D1.2の回想の絵・文章領域は既存のCSSを維持する。

## 再現

H24の正式保存を利用する。保存がない場合はH24の生成スクリプトで作る。rawと旧資料の `sourceSha256` が一致することを比較時に検査する。巨大な保存やraw資料はコミットしていない。

```sh
lab=works/ambertime/chronicle-lab
node --expose-gc "$lab/research-h25-generate.mjs" /tmp/h24-saves/wide-1200.json wide > /tmp/wide-raw.json
node --expose-gc "$lab/research-h25.mjs" /tmp/wide-raw.json /tmp/h24-facts/wide-1200.json > /tmp/wide-comparison.json
node --expose-gc "$lab/research-h25.mjs" /tmp/wide-raw.json --archive > /tmp/wide-recalls.json
node --test "$lab"/research-h25*.test.mjs
```

旧資料はH24の `research-h24-facts.mjs` で同じ正式保存から生成する。比較JSONには候補IDの全配列、採用IDと順序、境界、シード、未来の保持理由、回想文、根拠を残す。
