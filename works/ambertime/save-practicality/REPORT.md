# H1-A5 100年保存の実用性監査

基準main `306524e1e7df3a5b2e2ba27310fb269d6e15aa4a`。2026-11-05、研究専用profile・HTTP origin・保存キーで計測。本編・正式reader・形式・評判計算・乱数・既存保存・Productionは不変。

## 結論

**現行正式保存で全方針100年を安全に遊べるとは判定できない。実Chromiumで広域展開90年・100年のlocalStorage保存が失敗した。容量削減は次の独立研究の最優先課題である。** 地元・混合100年は書込・読戻・再読込・clean browser process再開が成功したが、実機の正式復元・通常操作・OS中断まで合格した意味ではない。

広域は60年成功・90年失敗のため、今回の観測点では最初の失敗は60年超〜90年以下。正確な月・単調な限界年は未確定。運営・他作品の同origin使用量・ブラウザ条件により変わる。100年以降は保証せず、内部上限を解除していない。

内部readerの拒否境界は **6,016,384 UTF-16 code units以上**。100年広域は5,838,093で残り178,291（約2.96%）しかない。writer側に同じ文字数チェックはなく、書込成功と読込可能性を同一視できない。

別originのnative localStorage探索では、研究キー1個で成功5,241,856／失敗5,242,880 code units、探索精度1,024。繰返しASCIIの試験と実ゲームJSONの失敗を別に記録した。これはその環境の観測であり全ブラウザの固定値ではない。混合100年はUTF-8約5.53MBでも保存でき、広域90年は内部上限未満でも保存できない。`navigator.storage.estimate()`のorigin quotaは10GiB、localStorage試験時usageは0と表示された。これをlocalStorage上限・実使用量と読むのは誤り。

IDBでは全12raw JSONを実書込・完全一致で読戻できた。originの概算usageは圧縮・実装の影響を受け、JSON論理bytesと一致しない。実IDB quota超過、端末ディスク枯渇は未検証。IDBに入ることは正式readerで高速復元できることでも、新方式を採用したことでもない。

## 保存失敗と再開

実native quotaで、広域60年の完全session→広域90年の書込失敗後、元60年のSHAを再読込・clean process再開まで維持した。保存のatomicな旧値保持を確認した範囲であり、OS kill・電断・origin削除の試験ではない。

現行アプリは一般保存失敗で時計停止・未保存表示・再試行/救出へ進む。汎用actは未保存の次状態をメモリに残し、candidate保存を使う納品/瓶詰め等は成功前に公開しない。candidate失敗の一部では古い「保存済み」表示が残る可能性がある。localStorageの比較→書込→読戻は複数タブに対して原子的CASではない。詳細・行番号・既存11件の失敗回帰は[SAVE-PATH.md](SAVE-PATH.md)。本編の修正はしていない。

## メモリ・性能・改善比較

[メモリ分析](memory-report.md)、[プレイ性能](play-performance.md)と各results JSONを参照。開始前・終了後のheap/RSS、処理時間、process high-waterを処理別に記録した。同期処理中の瞬間heap peakは計測しておらず、afterサンプルをpeakとは呼ばない。共有hostの単発/少数試行であり端末性能の推定値ではない。

広域100年の今回の正式cold復元は92.38秒、元JSONへ再保存一致。Node最大RSSは復元まで471.4MiB、一連処理後506.3MiB（同期heap peakやiPhone RAMではない）。warm serializer184.7ms、次月保存234.4msだった。詳細は[今回の正式復元](performance-report.md)。

月次12条件は実際に1か月進み、同入力3試行の結果SHAが一致。100年の月次モデル計算は数十msだが、正式JSON生成は約88〜225msの既存warm観測、cold readerは地元約42秒・広域約88〜91秒・混合約66〜69秒。帳面のcold projectionはさらに重い経路がある。検証済み同一依存のH1-A1証拠を再利用し、今回のブラウザIOと足し合わせたend-to-end時間を作らない。通常速度6秒・2倍速3秒/月の時計待機と実処理を分離した。1〜2時間の実プレイ、DOM/Canvas paint・フレーム・実機の応答は未検証。

## 100年運用の合格条件（提案、未採用）

数値は今回の問題を解消するための暫定budget。実機実測で見直す。安全余裕を性能の実測値と混同しない。

| 項目 | 次段階の条件 | 現状 |
|---|---|---|
| 容量 | 3方針100年の保存/正式復元/将来継続一致、実環境最小上限の70%以下を目安 | 広域90年で失敗。未達 |
| 余裕 | 移行前backup・新candidate・旧正常commit・GC一時容量を同時保持。100年時点30%以上の余裕を実測 | 広域内部余裕約3%、未達 |

## 次の実装順序

1. **評判容量削減を独立研究H1-Bとして最優先。** arrivals/events重複をID参照にできるか、参照閉包とserialization version/reader互換を調査する。次に古いattemptsの利用箇所を追跡し、保持が将来抽選に必要か確定する。最後に活動中評判と歴史記憶の分離を比較。今回削除・集約は行わない。
2. H1-Bは元完全JSONを保存し、3方針×30/60/90/100年、9世代境界と複数の将来分岐をoracle比較する。経済・販売数量/収入・評判・RNG・ID採番・seen/pending・因果/参照チェーン・H2-5候補/根拠/順序/seed/文章をすべて一致条件にする。容量だけ減っても不採用。
3. reader/writer上限対称化・失敗表示・未保存操作の確定契約と端末外backupを別の正式導入設計にする。既存上限の単純引上げは回避策にしない。
4. コピー削減・Worker bytes転送・段階処理をブラウザでphase別計測し、H1-A4の大fixture/128MiB crashを転送・parse・clone・hash・IDB毎に分割再現する。元crash phaseは今回も未確定。
5. checkpointの原子的IDB保存・依存失効・旧reader・完全backup・fallback・GCを統合し、同値/復旧を確認してからiPhone実機で実用budgetを検証する。checkpointだけで評判JSONが減るとは扱わない。
6. 正式保存への接続は別依頼・Planで実施する。今回のStagingマージは採用・実機合格・Production公開を意味しない。
