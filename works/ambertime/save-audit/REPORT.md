# H1-A1 容量・性能実測

Node v24.22.1 / linux x64。対象保存はH2-4のseed 42・同一政策で再生成し、12件のSHA-256とUTF-8容量をH24.mdと照合。

## 実測からの結論

保存容量の主因は操作履歴ではなく町の評判状態。100年のtownが全体の94.4〜96.0%、operationsは1.1〜1.7%。events/arrivals/attemptsは受領・反応・抽選のたびに蓄積し、上限のある製造帳簿より大きくなる。

初回復元の主因は全操作の適用・再計算。その中で全状態のstructuredCloneと、蓄積した履歴の再走査が繰り返される。JSON解析や最後のJSON一致検査だけを速くしても主因は残る。帳面の樽/歩みとraw回想抽出にも独立した全再生があり、表示件数を減らすだけでは資料生成負荷は減らない。

将来像はD（checkpointと歴史記憶の分離の併用）。ただし最初は正式保存を保ったままcheckpoint＋tailと再生contextの同値試験を行い、次に最近詳細・過去集計・不変の境界候補へ分離する。旧操作prefixや町の詳細は、その代替と将来計算/回想の一致が証明されるまで削除しない。具体的な依存表・A/B/C/D比較・H1-A2順序は[DEPENDENCIES.md](DEPENDENCIES.md)。

## 計測条件

sequential fresh processes; first complete official run discarded for host/cache priming, two measured cold-process runs; instrumented separate; extraction once; edits first discarded

各条件の最初の全復元をウォームアップ扱いで除外し、その後の2回を別々の新規Nodeプロセスで測定。各プロセスの検証cacheは空なので、JITはそれぞれcold。除外試行が温めるのは主にOSファイルcache。完全復元と再保存の全バイト一致を毎回検証。GCを計測前に明示実行、計測中GCは通常のV8管理。全条件を逐次実行し、他の研究benchmarkとの並列負荷を避けた。ホスト全体の他プロセス・GCタイミング・JIT差は制御していない。

計測内訳は別プロセスのソースinstrumentationで取得。元ファイルは変更せず、既知の境界をassertしてメモリ内に計測処理だけ追加。完全復元・全状態一致を維持する。applyOperation（経済・月次・乱数を含む再計算）とderived（captureNearby等）、core検証、最終状態比較、checkpoint生成を分離。structuredCloneの時間はこれらの**内数**であり足し合わせない。JSON解析は独立した事前解析の時間で、正式restoreMsにも再度含まれる。再保存は同じプロセスの検証済prefix cacheを利用するwarm値。

帳面は各条件1回のデータ生成計測。発売factsがcold検証、その後のcask factsは同じモジュールcacheを使用、cask/historyのobserverは全cold再生を行う。DOM・worker転送・paint・Safariは含まれない。回想資料抽出は1回、編集は4回中初回除外の3回。archive準備の前にmodule importを完了。archiveは各checkpointまでの全交代と周年を一括準備し、編集msは周年1回分。メモリはheap前後差とプロセスpeak RSSで、処理単独peakではない。解析済みの比較用複製、復元結果、再生cacheと再保存文字列を同時保持しており、復元だけの実使用量とは異なる。解析比較用の複製を保持する条件は復元中のGCにも影響し得る。H2-4の別host/別条件の秒数との差を高速化効果とは扱わない。iPhone Safari実機は未測定。
