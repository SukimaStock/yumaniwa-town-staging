# H1-A2 checkpoint＋tail 実測

12条件すべてで、研究checkpointから実際のtailを適用した正式状態・再生context・帳面資料・回想候補/境界/seed/採用順/文章が、同条件の全再生に一致した。研究用のローカル整合性検査であり、正式保存への導入や同等の永続checkpoint検証保証を証明するものではない。

## 環境と保証

Node v24.22.1 / linux x64。各条件を独立processで逐次実行し、未変更の正式readerによるcold復元1回を基準にした。統計的信頼区間はない。旧H1-A1の異なるhostの秒数から倍率を算出しない。全入力はH1-A1のSHAと容量に一致し、終了時にも不変を照合した。部分再生は正式復元・全資料再生後の同じwarm processで各1回実行し、資料付き再生は純粋tailの後に行った。JIT/import/OS cache条件はcold正式復元と異なる。状態だけの合計も、保守的に資料sidecarを含むファイルの読込/parseを計上する。

部分再生値はcheckpointのJSON読込/parse、ローカルhash・版・source/prefix照合、状態複製、tail適用、抽出途中/試飲の最終化、最終保存JSON一致を含む。純粋tailはobserverなしで別に再生し、帳面/回想collectorを使う資料付き再生と分けた。資料付きtail時間は通知とsnapshot複製を含む。collector自身の通知処理時間とhydrate時間も別記録した。

完全再生によるcheckpoint生成・独立した正式readerとの比較は研究の事前検証であり、毎回の部分再生時間には含めない。現行と同等の永続checkpoint信頼保証を実装した場合の復元時間は未実装のため不明。元保存・全操作prefixを保持し、容量削減は主張しない。

## 解釈と限界

- 年次・操作数・負荷方式はtailを短くする一方、作成頻度と大きな状態の複製・検証コストが増える。世代方式は境界を揃えやすいが、長いtailが残る。正式な閾値は未採用。
- 状態checkpointだけではprefixの帳面collectorや歴史根拠は復元できない。研究では別のprefix資料を保持した。
- peak RSSはprocess全体の累積最大で、正式状態・比較用コピー・複数checkpoint等を同時保持する。個別復元phaseの実機必要メモリとは異なる。heap前後差はresults.jsonに記録し、負の差もGCの影響を含む。
- ローカルhashは破損や誤接続を検出する。攻撃者が状態とhashを同時に作り直す場合の正当性証明ではない。
- 正式保存の圧縮・削除・移行、正式readerへの接続、Production変更、iPhone Safari実機確認は行っていない。
