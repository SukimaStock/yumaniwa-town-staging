# H1-B1 町の評判記録の重複整理

基準main `fcc14b249733b6cccd598bcd2e567e64848bcd7f`。研究専用codec・複製・profile・origin・keyで比較した。本編、正式reader/writer/形式/key、経済・評判・乱数・地図/帳面UI・C-3/D1.1/D1.2/H2-5、既存保存、Productionは変更していない。

## 判断

**重複を保存文字列から省いても、元の正式状態へバイト同一に復元できる。B/Cとも広域90年・100年の実localStorage保存に成功した。最小導入候補はC（派生一覧）とする。** 全12入力で到達一覧がeventsのarrival全件と同じ順序だったため、追加のID配列を保持するBより小さく、参照欠落の種類も増やさない。

ただし、広域100年Cは観測localStorage枠の約80.7%を使い、余裕約19.3%。70%参考値を満たしたとは扱わず、バックアップ2本同時保持は実容量不足。**「この変更だけで100年の単一保存を入れられる」は確認したが、「今後の増加・全ブラウザ・復旧まで十分」は未確定。** 容量不足からは改善した条件付き導入候補であり、無条件のケースA合格とはしない。同値不成立のケースCではない。

今回はこの最小候補の正式導入計画までで研究を止められる。attempts集約やDB再設計を次の必須作業にしない。19.3%が必要な運用余裕を満たさないと判断する場合に限り、次の独立研究としてattemptsの必要性を検討する。今回attemptsには一切手を加えていない。

## 重複の理由と依存

`event()`はevents.length+1でIDを採番しeventsへ追加する。`arrive()`は返された同じオブジェクトをarrivalsにも追加する。JSONの木構造として出力すると内容が二度書かれる。全時系列と到達一覧をそれぞれ使う実装上の役割は確認できるが、作者の過去の設計意図は推測しない。

到達一覧は単なる削除可能な表示cacheとして扱えない。地図到達段階・初海外到達・初期履歴の配列差分が利用し、量子化処理も巡回する。将来生成の主な状態はnodes/seen/pending/packets/attempts、採番はevents.length、因果はeventsのsourceIdである。全events・順序・他項目を維持し、正式計算へ渡す前にarrivalsを完全復元する。[全参照監査](DEPENDENCIES.md)。

## A/B/C比較

| 方式 | 保存表現 | 読込 | 互換性・複雑さ |
|---|---|---|---|
| A 現行 | events＋全arrival実体 | 現行状態 | 容量基準。広域90/100年で失敗 |
| B ID参照 | events＋arrivalsのID配列 | ID mapで実体を別オブジェクトへ複製 | 順序/部分一覧を表現可能。欠落/重複/型違いを拒否する必要 |
| C 派生 | eventsのみ、arrivalsを省く | arrivalを一回抽出、元のproperty位置に配列復元 | 全件・順序一致をencoderで必須検査。例外保存は拒否しAへ残す |

B/Cは研究version付きenvelope。正式readerは直接読めず、実移行は今回行わない。Cの元property位置を戻すmetadataを含めた容量を測った。runtimeは従来の完全状態のままであり、読込後の常駐メモリや月次計算が減ったとは主張しない。map・履歴呼出ごとの全件再走査は不要で、decode時に一度だけ一覧を再構成する。索引を正式永続化する設計は追加しない。

## 100年の余裕

native localStorage探索は別originで行い、成功5,241,856／失敗5,242,880 code units（精度1,024、研究key長29）。概算quotaと実書込は分けている。ここでの余裕はこの試験originで他の保存が無い場合の保守的下限との差。UTF-8 bytesや端末ディスク空き容量ではない。

広域100年Bも4,266,015単位で保存可能。B/Cのclean browser process再開も同じSHAで読戻した。C完全保存を別研究キーへもう1本書くと実QuotaExceededErrorとなり、元の1本は保持された。通常matrixの失敗Aは事前に研究キーを削除しており空状態保持の確認。非空値の失敗後保持はquota探索、完全な保存の保持は2コピー試験の結果として区別する。同originの別キーは余裕を共有する。既存本編キーで実験していない。

内部readerの6,016,384単位の拒否境界は別問題。研究wireは小さくても、展開した広域100年正式JSONは5,838,093単位のままで、余裕178,291（約2.96%）は増えない。新形式を公式readerへ直接通した実験ではない。正式導入時にwireと展開後の双方の制約を明文化し、上限を単純に解除しない。

## 同値・将来・歴史

12入力×A/B/Cの復元文字列が元正式JSONと全バイト一致し、入力SHAと全非arrival項目を保持した。[将来検証](FUTURE.md)は公開APIを実際に呼び、納品・月次・世代交代と3seed/複数商品で新規arrival・inquiry・visit生成後も各操作の完全JSON一致、ID重複なし、sourceId参照、配列順を確認した。町component試験を正式経済全体の試験へ水増ししない。

[歴史検証](history-report.md)では、100年3入力の完全復元とH1-A3から不変の53依存ファイルを照合。既存の完了したraw抽出証拠を再利用し、9世代境界×3案の27回の候補復元・編集を新規実行した。候補全体・根拠・ordinal/replayOrdinal・境界・seed・採用ID順・D1.2文を含むmaterial digestが一致。新たに100年全再生を27回行ったという意味ではない。採用場面のみを保持する方式にはしていない。

## 処理費用と保証範囲

容量・encode/decode時間・前後heap/RSS・process high-waterはcapacity-results.json。計測は同じNode processで条件が続く少数試行であり、瞬間heap peakやiPhone RAMではない。広域100年のdecode単発はA約57ms、B約112ms、C約139ms。strictなcanonical検査・parse・索引・clone・再文字列化を含む研究コード全体の費用であり、公式readerの全再生は含まない。容量削減が復元高速化を意味しない。

実Chromium153の36条件でB/C全成功、Aの広域90/100年のみnative quota失敗を再現。専用profileとローカルHTTP originを使用。WebKit/iPhone Safari実機、OS kill、物理電断、evictionは今回未検証。今回の容量方式は同origin全消失へのbackupを追加しない。

## 正式導入に向けた最小案（今回は実装しない）

1. 現行完全JSONを旧reader/writer契約として保持し、新しいversion付き保存envelopeのcodecだけでCを採用候補にする。正式ゲームモデル・arrivals配列のruntime契約は変えない。
2. 新readerは新形式を厳格検査→元状態へ展開→既存正式validationへ渡す。旧形式は従来どおり読む。Cの完全順序条件を満たさない入力は勝手に正規化せず旧形式を保持し停止/明示fallbackする。形式識別と元SHA/整合性の扱い、wire/展開後容量上限を明文化する。
3. writerは従来の正式状態検証を残し、その出力をCへ変換する。旧readerへ新形式を渡さない。既存データの変更は読込成功・全状態一致・書込確認後だけとし、失敗時に元値を守る。
4. 移行前backupは同originに2本置けない実測を前提に、端末外の読戻検証可能な書出、または旧値を保つatomic単一key置換の運用を別途決める。単一key旧値保持は外部backupの代替ではない。新規DBやcheckpoint導入を今回の方式の条件にしない。
5. 最小導入PRで12条件・将来分岐・9境界・quota失敗/再開を再検証し、作者のiPhone Safariで90/100年保存・正式復元・終了後再開を確認する。容量19.3%と内部展開余裕3%を許容する範囲、100年超の非保証を明記する。

ここまでで単一保存の100年と必要な失敗復旧の条件を満たせれば、追加の容量研究を増やさず導入できる。余裕が不足すると判断した場合だけattemptsの利用・集約を独立検証する。今回は正式導入、既存記録の移行、古い履歴削除を行っていない。
