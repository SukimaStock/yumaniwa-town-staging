## 2. Baselines and dependency trace

- Staging baseline: `45c58257604a214718a919c6732f9154e6020078`.
- Production baseline: `eb02129d4b4cb9fb10365d3bbb6bec999bebc96b`.
- Data and UI files are byte-identical between those baselines. Shared Engine v0.2 is
  also identical. Staging adds its weather debug module and migration notes; Production
  retains an unused local legacy Engine. These differences do not fix acquisition.
- `index.html` -> CodeaLite -> canonical `engine/sukimastock-engine.v0.2.0.js` ->
  work data/world/UI modules and animation extensions -> `sketch.js` -> weather scene.
- Scene `enter` creates/reuses UI, reads cache and stored cityState, then starts refresh.
  Selection is presets (Tokyo/London/New York by default), saved cities or city search.
  **No browser geolocation / permission request is used.**
- Browser directly calls `https://api.open-meteo.com/v1/forecast`; selected coordinates
  and timezone names are batched, up to eight cities. Five-day daily and hourly data,
  current temperature/condition/wind, UNIX times. No API key/proxy.
- Search uses `https://geocoding-api.open-meteo.com/v1/search`, 10s deadline, and persists
  chosen city's identity/coordinates in existing customCitiesV1. Query debounce/token
  prevents late search results replacing current results; an obsolete search may still
  complete. No speculative search concurrency rewrite was made.
- Forecast normalization updates cities atomically, then weatherCacheV1, UI city/world,
  and success event. Refresh freshness is 30 minutes; usable cache maximum age 12 hours.
  Failed requests retain old data and are retried on foreground update checks; manual
  refresh remains available. New listeners recheck on online / visible resume.
- No new API, Engine dependency, storage key/schema/version, external setting or shared
  analytics runtime was introduced. Existing per-city cache timestamps are authoritative.

API reference: https://open-meteo.com/en/docs (multiple coordinates -> array; single ->
object; documented timezone list; HTTP400 error object; WMO codes including 97).
Limits: https://open-meteo.com/en/pricing lists free-API limits and no uptime guarantee.
**Neither 429 nor a quota problem was observed in live checks.** Browser-side failures
cannot distinguish CORS, connectivity, DNS etc. without network logs; label is network.
No rate-limit stress test was run against the public service.

## 3. Confirmed failures and impact (before correction)

| Evidence / reproduction | User impact | Correction |
| --- | --- | --- |
| HTTP200 `{}` accepted; null temperature/code -> 0/clear | Demo or fabricated data became fresh OPEN-METEO and emitted success | Validate requested current data and displayed forecast arrays before atomic application; reject invalid/missing/null fields; retain prior valid data |
| Fresh outer cache timestamp + 13–15h-old individual forecast loads as fresh; malformed entries applied | Old/corrupt weather, wrong freshness, missing selected city fetch suppressed | Validate each cached forecast and its own age; refresh if any selected city lacks fresh data |
| Fetch resolves headers, json body never settles; timer already cleared | Loading lock indefinitely prevents manual and automatic refresh | Deadline races entire headers+body and aborts when available; late results cannot apply, even without AbortController |
| City added / selection changed during pending request | New city request deduplicated away; previous active city restored; global source label can claim real data for demo city | Snapshot requested membership, follow-up missing cities without overlap, retain current selection and use active city's provenance |
| Manual success then tone throws: Success + Error from one operation | Error may be unrelated to weather availability; incorrect failure state | Isolate ancillary audio exceptions; classify post-fetch world initialization separately as display |
| Failure keeps demo values or stale values; FAILED only in menu for 3s | Apparent normal weather can conceal unavailable data | Replace existing condition text with UNAVAILABLE and numbers with -- when no usable data; show CACHED + fetch time for stale data, including Ambient mode |

The sky animation remains decoration when weather is unavailable; no claimed measurement
is shown. Normal live layout, interaction, animation and audio levels are retained.
No modal, banner, permanent extra status surface or large loader was added.
Cache under 30m remains usable; cache 30m–12h is explicitly stale; older cache is hidden.
A structurally valid pre-fix cache that already contains falsely normalized demo values
cannot be distinguished retrospectively; existing 12h lifetime bounds it. No destructive
storage purge was added.

The response validators deliberately refuse incomplete forecasts rather than substitute
plausible demo numbers. Polar null sunrise/sunset is allowed (day/night uses is_day).
Device-clock-dependent two-hour response rejection was considered and removed during
review; no new client-clock age policy is imposed on API responses.

## 4. Event semantics and minimum improvement

Before: one Success after data/UI application, one Error for any rejection including
network/parse/normalize/UI/audio. Same UI deduplicates pending refreshes. Failed initial
loads can repeat roughly once per 60 foreground seconds and all attempts are counted.
Cache-only opens do not count success. The events do not denote sessions or cities.

Current Staging/Production HTML bootstrap, Engine staging guard and town host bridge were
traced: Staging suppresses outbound Plausible; host forwarding returns before standalone
send. No inherent duplicate sender was found. Historic 91-day mixing cannot be ruled out
from aggregate export alone, but current Staging traffic is suppressed. Direct Production
opens and town-frame opens both belong to the same Production dataset by design.

Corrections retain existing success/error event names and every attempted failure:

- Success: `outcome=initial|refresh|recovered`, `failed_attempts` capped at100,
  active `display_state=live|cached|unavailable`, plus existing source/count/duration.
- Error: `stage=fetch|display`, `error_type`, `display_state`, existing HTTP status,
  online flag, duration, source/count/custom-city boolean. An attempt fails definitively;
  this does **not** claim the session can never recover.
- `Weather Cache Display`: on scene entry when some selected city has usable cached
  data; count and active display_state (may be unavailable if only another city is cached).
- Automatic attempts wait at least60s after failure (numeric Retry-After respected up to
  30min); manual refresh remains explicit. Existing foreground checks plus resume/online
  recheck; no continuous background polling or immediate retry storm.

No city names, selected IDs, coordinates, search text, raw exception messages, user IDs,
session IDs or API keys are sent. All events are non-interactive. Success means acquisition
and world initialization completed, not certification of every subsequent canvas frame.
The new cache goal may need registration in the Plausible dashboard; custom-property
breakdowns require a plan that exposes them. No external dashboard settings were changed.
